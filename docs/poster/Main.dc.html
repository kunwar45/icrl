Summary

An AI agent acting in the world needs some way to tell harmful actions from harmless ones. Rather than write that rule by hand, I tried to learn it from 683 safe and 611 unsafe robot demonstrations in a simulated household. On tasks it had never seen the learned score reached an AUROC of 0.547. Counting a demonstration's steps reached 0.635.

What I did

1. Built a pipeline that generates robot demonstrations in the AI2-THOR simulator and verifies each against the simulator's object states.

2. Produced a verified dataset of 683 safe and 611 unsafe demonstrations across 159 household tasks.

3. Set up an evaluation that scores the model against simple baselines on the same data, which is what caught the failure.

1

The problem

AI agents can now carry out long sequences of physical steps on their own. Some of those steps cause harm: a knife into a blender, a stove left switched on. Writing a rule for every harmful action by hand does not scale.

Inverse Constraint Reinforcement Learning offers another route. Show the system safe demonstrations next to unsafe ones and let it learn a cost function Cθ from the contrast. Training then pursues task reward R while holding that cost down.

maximize  R(τ) − λ · Cθ(τ)
683 safe demonstrations 611 unsafe
learn from the contrast
Cθ, a scoring head on a frozen text encoder
test on unseen tasks never passed

Checking against simple baselines

This turned out to matter. My first evaluation gave the learned score an AUROC of 0.824, which read as a clear success. Counting steps gave 0.806 on the very same demonstrations.

Without the baseline, I would have reported a working safety score and moved on to fine-tuning against it.

2

Setup

Environment

AI2-THOR, a simulated household. The SafeAgentBench task set supplies 299 hazardous and 299 benign tasks over 84 scenes, and runs at 45.8 actions per second with no display attached.

Ground truth

The simulator's own object states: isBroken, isToggled, isSliced, isFilledWithLiquid. I do not use the benchmark's language-model scorer.

Demonstrations

Generated by Qwen2.5-32B-Instruct on four L40S GPUs, the same model for both classes, 5 to 10 demonstrations per task.

Held-out split

By task, chosen once and applied to both classes. Two demonstrations of one task look almost identical, so splitting by demonstration would leak the test set into training.

4

What I ruled out

Data quality

Three passes over the first 700 demonstrations found six silent bugs, among them 132 interrupted hazards recorded as refusals. I fixed all six and regenerated everything. The result did not move.

Hidden shortcuts

Length, reward, no-ops and contamination between splits are all closed. The encoder had been handed the text Task <id> as a fallback, which scored 0.80 on its own. I removed it.

Model capacity

A regularized version of the scoring head reached 0.438, so the model is not too small for the job.

Task variety

At 21 usable benign tasks the score reached 0.828 on training tasks and 0.511 on held-out ones, so it had memorized the task list. I widened the verifiable pool from 237 to 523 and tripled the expert count from 52 to 159. The result did not move.

An AUROC of 0.547 means the score ranks unsafe above safe only slightly more often than chance. Its average score is actually higher for the safe demonstrations.

What this means

A safety score built on a frozen text encoder and trained by comparing whole demonstrations does not carry over to new tasks here. Three things to try next: train the encoder instead of freezing it, compare safe and unsafe versions of the same task, and label individual steps rather than whole demonstrations.
